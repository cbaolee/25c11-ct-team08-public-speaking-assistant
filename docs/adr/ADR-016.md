# ADR-016: Real Schedule on the core project, server-side check-in and done, one reminder email per session

Trạng thái: đã chốt (28/11/2026, issue #135). Liên quan: ADR-011, ADR-012, ADR-013, R6;
`src/web/static/js/schedule/schedule_model.js`, `src/web/static/js/schedule/schedule_store.js`,
`src/app/schedule/rules.py`, `src/app/schedule/mailer.py`, `src/app/routes/schedule.py`,
`src/app/db/` (`ScheduleRepo`), `src/app/auth.py` (`email_for_user`),
`db/migration_main/0012_schedule.sql`, `db/migration_main/0013_schedule_reminder_cron.sql`,
`app_constants.toml` `[schedule]`.

## Bối cảnh

- The Schedule demo keeps events and check-ins in `localStorage`. Data is lost on another device,
  the user can change the clock to check in or mark a session done, and no reminder email exists.
- The rules already exist in `schedule_model.js`: 6 h check-in window that never crosses midnight,
  reminder 30 min before start (08:00 for an all-day session), schedule lock from the reminder,
  details lock from the start, "skipped" when the event was set after its reminder time.
- Part 1 (rules in Python, mailer, `schedule_api.js`, screens) and Part 2 (tables, API, reminder
  job) are built in parallel. Both sides need one fixed contract before they start.

## Quyết định

### 1. Storage on core `psc-main`

- All three tables live on core, not on the shards of ADR-012.
- Reasons: one pg_cron job reads every user's events in one query; `on delete cascade` from
  `auth.users` cleans the data when an account is deleted; the "done" check only reads one session
  by id through `repos.sessions`, which already picks the right shard.
- Size is small (one event row is under 1 KB; check-ins and reminders are one row per session).
- **Rejected:** schedule on the user's shard. The cron job would have to call 9 projects, and
  deleting an account would need a cleanup step per shard.

### 2. Time zone

- Each event stores `timezone`, an IANA name sent by the browser
  (`Intl.DateTimeFormat().resolvedOptions().timeZone`). The server rejects a name that
  `zoneinfo.ZoneInfo` cannot open (422 `validation_failed`, field `timezone`).
- **Local columns** (wall time in the event's `timezone`): `start_date`, `start_time`, `end_until`,
  `occ_day`, and the `{day}` path parameter.
- **UTC columns** (`timestamptz`): `schedule_set_at`, `details_edited_at`, `created_at`,
  `updated_at`, `checkin_at`, `done_at`, `attempted_at`, `sent_at`.
- The server works in UTC (`datetime.now(UTC)`) and converts with `zoneinfo`. It never trusts a
  time sent by the client. JSON timestamps are ISO 8601 UTC, for example `2026-11-28T09:30:00Z`.
- A local time that does not exist or exists twice (DST change) uses `fold=0`, the Python default.

### 3. Occurrence key

- `"{event_id}@{YYYY-MM-DD}"`, the same as the demo. `YYYY-MM-DD` is the local day of the session.
- In the database the key is the pair `(event_id, occ_day)`; the string form is only used in
  Python and JS.

### 4. Tables (`0012_schedule.sql`)

`schedule_events`

| --- | --- | --- |
| `id` | `uuid` pk | `default gen_random_uuid()` |
| `user_id` | `uuid not null` | `references auth.users(id) on delete cascade` |
| `start_date` | `date not null` | local |
| `all_day` | `boolean not null` | |
| `start_time` | `time null` | null exactly when `all_day` |
| `timezone` | `text not null` | IANA name |
| `duration_min` | `smallint null` | `in (5, 10, 15, 20)` |
| `category` | `text not null` | `any`, `cinematography`, `gender_studies`, `information_technology`, `learning_experiences`, `sports`, `wildlife` |
| `color` | `text not null` | `lime`, `blue`, `green`, `amber`, `brown`, `red`, `slate`, `gray`, `sky` |
| `script_kind` | `text not null` | `free`, `saved`, `ai` |
| `script_id` | `uuid null` | set when `saved` |
| `script_title` | `text null` | set when `saved` |

| `repeat_kind` | `text not null` | `none`, `daily`, `weekly`, `custom` |
| `repeat_days` | `smallint[] not null default '{}'` | each 1–7 (ISO weekday); not empty for `custom`; empty for other kinds |
| `end_kind` | `text not null` | `never`, `until`, `count`; `never` when `repeat_kind = 'none'` |
| `end_until` | `date null` | set only for `until`; `>= start_date` |
| `end_count` | `smallint null` | set only for `count`; 1–99 |
| `schedule_set_at` | `timestamptz not null default now()` | last change of date, time, all day or repeat |
| `details_edited_at` | `timestamptz null` | last change of any other field |
| `created_at`, `updated_at` | `timestamptz not null default now()` | |

`script_id` matches `scripts.id` (`uuid`) but has **no foreign key**: deleting a saved script must
not delete or block the event, and `script_title` keeps the name shown in the calendar.

Extra checks, taken line by line from `isValidEvent` and `normalizeRecurrence`:
`script_kind = 'ai'` needs `duration_min is not null and category <> 'any'`.

`schedule_checkins`: `event_id uuid references schedule_events(id) on delete cascade`,
`occ_day date`, `user_id uuid not null references auth.users(id) on delete cascade`,
`checkin_at timestamptz not null`, `done_at timestamptz null` (`>= checkin_at`),
`session_id uuid null` with **no foreign key** (the session may be on a shard),
`primary key (event_id, occ_day)`.

`schedule_reminders`: `event_id uuid references schedule_events(id) on delete cascade`,
`occ_day date`, `status text not null` (`sent`, `failed`, `skipped`),
`attempted_at timestamptz not null`, `sent_at timestamptz null`, `primary key (event_id, occ_day)`.

- RLS on for all three tables with **no policy**; only `service_role` (the app server) reads and
  writes. Index on `schedule_events(user_id)` and `schedule_checkins(user_id)`.
- "This and following" edit is one SQL function `split_schedule_event(...)` called by `rpc`, so
  cutting the old event and adding the new one happen in one transaction (no lost or doubled
  session, no second email).

### 5. API

Every `/api/schedule*` route needs a logged-in user; `user_id` always comes from the token. An
event of another user gets the same 404 as a missing one. Errors use the shape
`{"error_code": "...", "message": "..."}`.

**Event JSON** (the same nested shape as the demo, so `validate_event` keeps the demo field keys):

```json
{
  "id": "uuid",
  "date": "2026-12-01", "time": "19:30", "all_day": false, "timezone": "Asia/Ho_Chi_Minh",
  "duration_min": 10, "category": "sports", "color": "lime",
  "script": {"kind": "saved", "script_id": "uuid", "title": "My pitch"},
  "note": "",
  "recurrence": {"kind": "weekly", "days": [], "end": {"kind": "count", "count": 5}},
  "schedule_set_at": "2026-11-28T09:30:00Z", "details_edited_at": null
}
```

`script` is `{"kind": "free"}`, `{"kind": "ai"}` or the saved form above. `end` is
`{"kind": "never"}`, `{"kind": "until", "until": "YYYY-MM-DD"}` or `{"kind": "count", "count": n}`.

| # | Method and path | Request | Success |
| --- | --- | --- | --- |
| 1 | `GET /api/schedule?from=YYYY-MM-DD&to=YYYY-MM-DD` | query, `to >= from`, at most `range_max_days` (62) | 200 `{"events": [event], "checkins": [{"event_id", "occ_day", "checkin_at", "done_at", "session_id"}], "reminders": [{"event_id", "occ_day", "status", "sent_at"}]}` |
| 2 | `POST /api/schedule/events` | event without `id`, `schedule_set_at`, `details_edited_at` | 201 event |
| 3 | `PATCH /api/schedule/events/{event_id}/occurrences/{day}` | only the changed fields | 200 `{"events": [...]}`: the edited event, or the cut old event and the new one |
| 4 | `DELETE /api/schedule/events/{event_id}/occurrences/{day}` | none | 204 |
| 5 | `POST /api/schedule/checkins` | `{"event_id", "day"}` | 200 `{"event_id", "occ_day", "checkin_at", "done_at": null, "session_id": null}` |
| 6 | `POST /api/schedule/checkins/{event_id}/{day}/complete` | `{"session_id"}` | 200 check-in with `done_at` and `session_id` |
| 7 | `POST /internal/schedule/reminders/run` | header `X-Cron-Secret` | 200 `{"sent": n, "skipped": n, "failed": n}` |

- `GET` returns events whose `start_date <= to` and whose `series_until` is null or `>= from`.
- `PATCH` and `DELETE` follow `editOccurrence` and `deleteFromOccurrence`: an event that does not
  repeat, or the first session of a series, is changed or deleted whole; a later session cuts the
  old event (`end = until` the day before) and, for `PATCH`, starts a new event on `day`. For
  "After N" the new event gets `rules.remaining_count`, not N.
- Request bodies forbid unknown keys (`extra="forbid"`).

| Error code | HTTP | When |
| --- | --- | --- |
| `validation_failed` | 422 | `validate_event` fails, bad `timezone`, bad range; body adds `"fields": {"start": "past", ...}` with the keys and codes of `validate_event` |
| `schedule_limit` | 409 | the user already has `max_events_per_user` events |
| `schedule_locked` | 403 | change of date, time, all day or repeat when `not can_edit_schedule` (from `reminder_at`) |
| `details_locked` | 403 | any other change, or delete, when `not can_edit_details` (from start) |
| `not_started` | 409 | check-in before start |
| `window_closed` | 409 | check-in at or after `window_closes_at` |
| `not_checked_in` | 409 | `complete` without a check-in |
| `session_not_found` | 404 | the session does not exist or belongs to another user |
| `session_not_scorable` | 422 | session not `ok`, no `overall`, or created at or before `checkin_at` |
| `event_not_found` | 404 | event missing, of another user, or `day` is not one of its sessions |
| `rate_limited` | 429 | more than `writes_per_window` writes in `window_s` (bucket `schedule_write`) |
| `not_authenticated` | 401 | no valid access token (from `get_current_user`); route 7: wrong or missing `X-Cron-Secret` (no reason given) |
| `storage_unavailable` | 503 | the database cannot be reached (`StorageError`) |
| `cron_unconfigured` | 503 | route 7: `SCHEDULE_CRON_SECRET` is not set (logged once) |

- Check-in again returns the old row and never changes `checkin_at`.
- Rate limit uses `repos.rate_limits.hit` with the SHA-256 hex of the user id, and fails open like
  ADR-013.

### 6. Cron

- `0013_schedule_reminder_cron.sql`: `pg_cron` job `schedule_reminders`, `*/5 * * * *`, calls
  `net.http_post` (`pg_net`, `timeout_milliseconds` 30000) to `POST /internal/schedule/reminders/run`
  with header `X-Cron-Secret`.
- App URL and secret are read from Vault (`vault.decrypted_secrets`); the file never holds them.
  The server compares the header with `SCHEDULE_CRON_SECRET` using `hmac.compare_digest`.
- Running the file again replaces the job (same name). Remove with
  `select cron.unschedule('schedule_reminders');`.

### 7. Reminder: at most one email per session

- Each run takes sessions of "today" and "tomorrow" **in each event's `timezone`** whose
  `reminder_at` is in `(now − reminder_grace_min, now]` and with `now < start`.
- `schedule_set_at > reminder_at`: write `skipped`, send nothing.
- User with `preferences.email_reminders` set to `false`: no row, no email (checked before the
  claim). A missing key means "on".
- Otherwise **claim first**: insert the row as `failed` with `on conflict do nothing`. Only the run
  that inserted the row sends. Success sets `sent` and `sent_at`; `MailError` or no email address
  keeps `failed`.
- A claimed row is **never sent again**, even when `failed`. Losing one reminder is better than two
  emails.
- Logs only hold counts (`sent=… skipped=… failed=…`), never email, name or note (R6).

### 8. Done verified by the server

`complete` marks a session done only when all are true:

1. A check-in exists for `(event_id, day)`, else 409 `not_checked_in`.
2. `repos.sessions.get_session(user.id, session_id)` returns the session, else 404 `session_not_found`.
3. `status == "ok"` and `overall is not None`, else 422 `session_not_scorable`.
4. `session.created_at > checkin_at` (both UTC), else 422 `session_not_scorable`.

- The window is not checked again: an evaluation that ends after the window closes still counts,
  like `occurrenceStatus` in the demo.
- A second call on a done session returns the old row and changes nothing.

### 9. Signatures that Part 2 calls

`src/app/schedule/rules.py` ports `schedule_model.js` to Python without changing any rule.
`event` is the stored event (dict or model), `occ` is an occurrence dict with `key`, `event_id`,
`day`, `start` (aware UTC `datetime`), `all_day`, plus the event fields. All times are aware.

### Constants

Rule values stay as in `schedule_model.js`: `checkin_window_h = 6`, `reminder_lead_min = 30`,
`all_day_reminder_hour = 8`, `note_max_chars = 200`, `count_max = 99`, one email per session.
Values in `app_constants.toml` `[schedule]` that are **provisional** (not measured yet):

`range_max_days = 62` covers two calendar months.

## Hệ quả và giả định chưa kiểm

- The demo `localStorage` data is not moved to the server; users start with an empty schedule.
- Without an internet connection the Schedule screen cannot load or change events.
- pg_cron runs every 5 min, so a reminder can arrive up to about 5 min after `reminder_at`. If the
  server sleeps longer than `reminder_grace_min`, that reminder is lost, not sent late.
- A server crash after the claim and before sending loses that one reminder (row stays `failed`).
- An event moved to another time zone keeps the old `timezone` until the user edits it.
- Not tested on Supabase yet: `0012`, `0013`, pg_cron, pg_net, Vault, `on conflict do nothing`
  through PostgREST. Both files must run on `psc-main` before deploy.
- Free Supabase projects pause after a week without use; a paused core project sends no reminder.
