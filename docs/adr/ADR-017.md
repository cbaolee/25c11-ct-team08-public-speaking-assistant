# ADR-017: Gibberish guard, category guard and Generate at Turn 1

- Status: Proposed
- Date: 2026-11-28
- Refs #120, #121. Use cases UC2 (Content Validation) and UC3 (Generate Script). Related: [ADR-014](ADR-014.md),
  [ADR-015](ADR-015.md).
- Code: `src/text_processing/input_guard.py`, `src/text_processing/category_guard.py`, `src/app/script_guards.py`,
  `build_turn1_decision` in `src/text_processing/chat_session.py`, `src/app/main.py`, `app_constants.toml`
  `[script_guard]`.

## Context

Junk such as `asdfghjkl` could reach moderation, embeddings, the LLM and the rate limit counters. Nothing compared the
material with the selected category. Turn 1 never allowed Generate, even with a sufficient prompt or file.

## Decision

### 1. Gibberish guard (contract E v2.1)

Text is NFC normalised and split into words. A core is a word without leading and trailing characters that are neither
letter nor digit. The first matching row decides.

| Rule | Condition | Result |
|---|---|---|
| - | A file is attached, or the text is empty | allow |
| EXEMPT | The whole message (lower case, final `.!?` removed) is `generate`, `done`, `tạo`, `xong`, `yes`, `no`, `ok`, `okay` or `sure` | allow |
| R1 | No letter and no digit | refuse |
| R4 | At least 4 cores, all equal (case ignored) | refuse |
| T1-T4 | At least one core has a letter, and every such core is junk by one of the rules below | refuse |
| - | Anything else | allow |

| Junk rule | A core is junk when |
|---|---|
| T1 | one letter repeats at least 5 times in a row |
| T2 | it has at least 6 letters and at most 2 different ones |
| T3 | its letters (marks removed) are all `a-z` without `a e i o u y`; at least 6 letters, or 8 if all caps |
| T4 | its letters contain 5 neighbouring keys of one QWERTY row, either direction, or the whole core is such a run of at least 4. A longer run contains a run of 5, so only windows of 5 are scanned |

- Whitespace is U+0009 to U+000D plus categories `Zs`, `Zl`, `Zp`. U+001C to U+001F, U+0085 and U+FEFF are not.
- Only T3 is limited to Latin letters. T1, T2 and R4 apply to every script.
- Checked: `prompt` on `/api/script-chat/suggest`; `message` on `/api/script-chat/message` and `/message/jobs`;
  `user_feedback` and `raw_text` on `/api/generate-script`. A "file" means parsed chunks on the chat routes. On
  `/api/generate-script` it is an upload named `.pdf` that is not empty (its content is not validated yet).
- It runs before moderation, embeddings, LLM calls, session writes and rate limit counting: 422 `gibberish_input`.
- Rule numbers are module constants, not TOML settings: the planned web copy must not import anything. Both sides are
  meant to agree through `tests/fixtures/gibberish_vectors.json` (75 cases). Only Python reads it so far.

| Known behaviour | Examples |
|---|---|
| Passes (miss) | `ajsdhakjsdh`, `cat dog table blue`, `aaaaa ok`, `12121212`, `bla bla bla` |
| Refused when it is the whole message | `booboo`, `deeded`, `xxxiii`, `wert`, `hahaha`, `sooooo`, `tp.hcmc`, `5 5 5 5` |

### 2. Category guard

The goal is to limit false blocks: stop only clear mismatches. Three cases pass early, without scoring: the category is
not one of the six (for example `free`), a template of the category matches, or the material has fewer than 8 words with
a letter.

Layer 1 is local (sentence embeddings, cosine similarity). The prototypes are 7 hand-written sentences per category, no
template titles. `selected` is the best passage (prompt sentences and chunks, at most 20, sampled evenly) against the
selected category. `best_other` compares one vector of the whole text, cut to 1500 characters, with the other five.

| Zone | Condition | Result |
|---|---|---|
| Safe | `selected >= 0.16`, or `best_other < 0.35`, or `best_other - selected < 0.20` | allow |
| Block | not safe, `selected < 0.16` and `best_other >= 0.42` | 422 |
| Gray | everything else | layer 2 where allowed, otherwise allow |

| `[script_guard]` key (prefix `category_guard_`), all **provisional** | Value |
|---|---|
| `safe_selected_min`, `safe_other_max`, `safe_margin_max` | 0.16, 0.35, 0.20 |
| `block_selected_max`, `block_other_min` | 0.16, 0.42 |
| `min_words`, `max_chars`, `max_segments` | 8, 1500, 20 |
| `llm_max_tokens`, `llm_timeout_s` | 80, 5 |

`block_selected_max` equals `safe_selected_min`, so the `selected` condition of the block zone is now redundant.

Layer 2 asks `groq_compaction_model` about gray cases (`reasoning_effort="low"`). It blocks only on agreement:
`fits_selected` is `false` and `better_category` equals the `best_other` category of layer 1. The system prompt asks for
`fits_selected=true` when the text names no specific topic. The 5 s timeout applies to each HTTP phase, not to the whole
call, and the SDK does not retry this call; the key pool can still try another key. Every error in either layer fails
open (no local model, encoding error, no Groq client, no token budget, failed call, invalid answer).

**Verified content.** The content of a session is its first prompt, file names and chunk count. It is verified for a
category when a check of it passed by layer 1 or layer 2, or by a template match on `/suggest`. A skipped check (too
short, unknown category) and a fail-open do not count.

**Rule for added files** (user decision, 2026-11-28, after the second review; it changes the earlier rule, which scored
every new file): the message and the new file chunks are scored **only while the session has no verified content for the
category**. Once it has, a further file on `/message`, `/message/jobs` or `/suggest` is not scored and passes. Reason:
a supporting file such as a grading rubric was blocked by mistake (in review: `selected` 0.113, `best_other` 0.566
under `wildlife`). Both branches are tested in `tests/test_script_api.py`:
`test_without_verified_content_the_note_and_new_file_are_scored_alone` and
`test_with_verified_content_the_same_new_file_passes_unscored`.

| Route and case | Material scored | Layer 2 |
|---|---|---|
| `/suggest` without a new file | first prompt, new prompt and session chunks together | yes |
| `/suggest` with a new file, not verified | this request's prompt and the new file only | yes |
| `/suggest` with a new file, verified, new prompt differs from the first | first prompt, new prompt and old chunks; not the file | yes |
| `/suggest` with a new file, verified, prompt empty or unchanged | nothing | - |
| `/message`, `/message/jobs` with a new file, not verified | that message and that file | yes |
| `/message`, `/message/jobs` without a file, or verified | nothing | - |
| `/generate-script` with a session | session category, first prompt and chunks, only if no stored decision covers them; `raw_text` always, on its own | never |
| `/generate-script` without a session | form category, `topic` and `raw_text` | never |

- The chat routes check after moderation and before the session changes.
- Template pass: on `/suggest`, the prompt (without one, the first stored and new chunks) strongly matches a template of
  the category; it applies whenever `/suggest` would score. On the other routes, the session already selected a template
  of its category; `/message` looks at it only while not verified, and on `/generate-script` it also skips `raw_text`.
- Decisions are kept in an in-RAM LRU with the capacity and sliding lifetime of the chat session store: category slug,
  a hash of the content (never the content) and a verified flag. Only `/suggest` and the message routes store them.
- A file accepted into a verified session stores a verified decision for the new content. A too-short pass is stored as
  not verified: `/generate-script` skips that content, but later files are still checked. Checking the same content
  again never removes the flag.
- Nothing is stored after a fail-open or a template pass on `/message`. When the session is not verified and only new
  material was scored, older content also needs a stored decision for the category, except after a template pass on
  `/suggest`.
- The 422 `category_mismatch` body has `error_code`, `message`, `selected_category`, `selected_category_label`,
  `suggested_category` and `suggested_category_label`. `/message/jobs` answers 202, and the failed job snapshot carries
  the same fields.
- Guard logs hold slugs, layer, result, rounded scores and exception class names, no user text.

### 3. Generate at Turn 1

| Mode and case | LLM asked | `can_generate` = `ready_to_generate` | `topic_clear` |
|---|---|---|---|
| Template complete: no missing entity, coverage not below `slot_coverage_ready_threshold` | no | true | true |
| Template incomplete | yes | false | true |
| Write Freely, no topic yet | no | false | false |
| Write Freely, topic, no file, under 40 words | yes | true only if it answers `sufficient: true` | true |
| Write Freely with a file, or at least 40 words | yes, for the reply | true | true |

- When the LLM should be asked but is unavailable, a fixed reply is used. Of those rows, only the last stays `true`.
- `topic_clear` is deterministic: a file, or at least 2 words of the first prompt that are neither meta words (`help`,
  `speech`, ...) nor lengths such as `5-minute`. The LLM has no say in it. Word counts here include only words with a
  letter.
- `free_topic_turn1_ready_words = 40` (provisional) differs from `free_topic_min_words = 150`, the rule-based fallback
  from Turn 2. So `ready_to_generate` can be `true` at Turn 1 and `false` at Turn 2 when Groq fails.
- The backend does not block `/api/generate-script` on readiness. Turn 2+ is unchanged.

## Calibration

Layer 1 only, measured on 2026-11-28. **The 64 cases were drafted by AI and no human has reviewed them.**
`safe_selected_min` and `block_selected_max` (0.16) were chosen on this same set, with no held-out set, so the numbers
are more optimistic than real use. The other thresholds were not tuned. The author of the 64 cases had read the
hand-written prototypes. Source: `tests/fixtures/category_guard_eval_set.json`.

| Cases | Observed |
|---|---|
| 30 on-topic and 15 scored interdisciplinary (1 short case skipped) | 0/45 on-topic and interdisciplinary cases were blocked by mistake on the AI-drafted 64-case set |
| 18 mismatch | 7/18 blocked, all 7 suggesting the expected category; 11/18 not blocked by layer 1 (3 gray, 8 safe) |
| `no_topic`: 10 AI-drafted sentences (2 found by a reviewer) under each of 6 categories | 0/60 blocked, 6/60 gray |

The user chose 0.16 over 0.20 to limit false blocks: with the hand-written prototypes it keeps the nearest legitimate
case farther from the block zone (0.113 against 0.073 at 0.20), although it blocks fewer mismatches (7/18 against
12/18).

- The guard stops only the clearest mismatches. Mismatch cases lie close to the block thresholds on both sides, so
  small changes move the result.
- Layer 2 was **not** evaluated. A smoke test on 2026-11-28 (3 real requests, short synthetic sentences, not
  reproducible from the repository) only showed that answers arrive: all finished with `stop`, used 44-47 of 80 output
  tokens (23-27 reasoning) and took 0.59-0.91 s. The topicless and interdisciplinary sentences got
  `fits_selected=true`; the clear mismatch got `false` with `better_category=null`, so it was allowed.
- Next: more cases, human review of the labels, a held-out set, tuning again, an evaluation of layer 2.

To run again (the `integration` test is not part of CI): `HF_HUB_OFFLINE=1 uv run python scripts/eval_category_guard.py`
and `HF_HUB_OFFLINE=1 uv run pytest -m integration tests/test_category_guard_eval.py`.

## Consequences and known limits

- Layer 2 was not tried with long text; 80 output tokens may then be too few, which fails open.
- A 429 on the layer 2 call locks that key for this model at once (`exhausted_cooldown_s`), so compaction and other
  calls that use the same model and key pool lose it too. Layer 2 also shares their token budget limiter.
- Gray cases send up to 1500 characters of the prompt or document to Groq (risk R6). The consent popup does not mention
  this yet.
- The first request waits if the warm-up has not finished. Encoding the 42 prototypes took about 0.13-0.25 s on one
  developer machine (evaluation script), model loading not included.
- Files added to a verified session are not category-checked.
- A first prompt of 8 words or more that names no topic can become verified, which lets later files in unchecked.
- A new prompt that drifts far off the category, sent without a file or to a verified session, is scored together with
  the first prompt and can be masked by it: it passes, and so does Generate.
- On `/suggest`, a template match lets an off-category new file through and counts as verified, also when the match
  comes from older chunks because there is no prompt.
- A decision expires `chat_session_ttl_s` after its last renewal, and only the category guard renews it, while any
  turn keeps the session alive. Later files are then checked again, and `/generate-script` runs layer 1 on the session
  content, so a file that was let in unscored can answer 422. A restart loses sessions and decisions alike; neither is
  shared between workers.
- Not category-checked: messages without a file; a new PDF and `user_feedback` on `/generate-script`; the form `topic`
  and `category` there when a session exists. `/generate-script` does not run the gibberish guard on `topic`.
- Open: when Write Freely first asks for the topic, `session.topic` stays the first prompt. The topic rule asks again
  after a one-word topic such as `Football`.
- Only the system prompt keeps an LLM reply from inviting Generate when `can_generate` is `false`.
- The web UI does not handle `category_mismatch` yet and shows no Generate button at Turn 1 (separate web PR).

## Alternatives considered

| Alternative | Why not chosen |
|---|---|
| Check the category on every message | A short answer can look off-topic on its own (not measured); the goal is few false blocks |
| Call Groq on `/generate-script` | Generate would depend on one more provider call and its token budget |
| Template titles as extra prototypes | At 0.20 they blocked 9/60 `no_topic` rows (hand-written only: 0/60) and 5/18 mismatches (hand-written only: 12/18). Probe script outside the repository, not reproducible from it; the `no_topic` rows were used to make this choice |
| Constants at the end of `[script]` | Parallel work adds keys there; a separate `[script_guard]` section avoids the conflict |
| Gibberish rules in `parser.py` | `parser.py` handles documents; a small module is easier to mirror in the web client |
| Trust a `topic_clear` from the LLM | The fixed rule works without Groq, is testable and needs no call for an unclear prompt |
