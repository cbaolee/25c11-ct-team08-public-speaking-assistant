# ADR-002: Report save status in the `/api/evaluate` response (schema 2.1)

- **Status:** Accepted
- **Date:** 2026-11-15
- **Scope:** `POST /api/evaluate`, `src/audio_processing/result_schema.py`

## Context

`POST /api/evaluate` now saves every scored session to the user's history (audio, chart series and the session row). The frontend needs two things from the same response:

1. The `session_id`, to open or delete the session later.
2. Whether saving worked, so it can warn the user without hiding the score.

Saving can fail (encoding, upload, database) after scoring has already succeeded. A failed save must never lose the evaluation result.

## Decision

Add two fields to `EvaluationResultV2` and raise `schema_version` from `"2.0"` to `"2.1"`:

| Field | Type | Saved | Not saved |
| --- | --- | --- | --- |
| `session_id` | `str \| None` | the new session UUID | `null` |
| `saved` | `bool` | `true` | `false` |

- Both fields have defaults (`None`, `False`), so the Evaluate Pipeline builds results without knowing about storage. The route fills them with `result.model_copy(update=...)` after a successful save.
- A save error is logged and the response is still HTTP 200 with the full result, `saved: false` and `session_id: null`. The UI shows the Report with a "Could not save to history" toast.
- `insufficient_audio` results are also saved as a row (without audio) and follow the same rule.
- `POST /api/baseline` is not affected and stays at `"2.0"`.

## Consequences

- The response shape stays flat: existing UI code that reads score fields keeps working.
- Clients and tests that check `schema_version == "2.0"` for evaluate results must accept `"2.1"`.
- Compacting old sessions runs after the new session is saved; a compaction error does not change `saved`.

## Alternatives considered

- **Wrap the result in an envelope** (`{"result": ..., "session_id": ..., "saved": ...}`): breaks every UI path that already reads the result directly.
- **Return the session id in an HTTP header:** easy to miss, not part of the JSON contract, and harder to test.
- **Let the client save the session with a second request:** a closed tab or network error loses the session, and the client would have to upload the audio a second time.
