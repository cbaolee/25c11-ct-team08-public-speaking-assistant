# ADR-012: Chia DB thành 1 core + 9 shard theo user

Trạng thái: đã chốt (23/11/2026). Liên quan: ADR-001, ADR-011; `db/migrations/0010_accounts.sql`,
`db/migrations/shard/`, `src/app/config.py`, `src/app/db/sharding.py`, `src/app/db/factory.py`,
`src/app/db/repositories.py`, `src/app/db/memory.py`, `src/app/db/supabase_repo.py`,
`src/app/routes/auth.py`.

## Bối cảnh

- Một project Supabase Free có 500 MB Postgres và 1 GB Storage. Mỗi organization chạy tối đa 2 project.
- Mức trần một user (10 session full, 30 compact, 10 saved script, audio tối đa 1 920 s): ~29,8 MB
  Postgres và ~83,2 MB Storage. 100 user ở mức trần cần ~2 981 MB Postgres và ~8 324 MB Storage.
- Storage là giới hạn chặt hơn: 8 324 / 1 024 = 8,1, nên cần tối thiểu 9 project cho session.
  Core đã giữ phần lõi của mọi user, nên session của user mới chỉ chia cho 9 shard.
- Audio và series chiếm 92% dung lượng; profile, baseline, script nhỏ và có giới hạn cứng.

## Quyết định

1. **1 core + 9 shard, chia theo user.**
   - Core (`psc-main`): Auth, `accounts`, `profiles`, `baselines`, `scripts`, bucket `avatars`,
     `baselines`. Core **không nhận session của user mới**. Core vẫn có `sessions`, bucket `audio`,
     `series` cho các user đã có trước khi chia shard (shard ref `core`); nhóm sẽ quyết định sau có chuyển
     họ sang shard hay không.
   - 9 project shard (`psc-shard01` … `psc-shard09`): chỉ có `sessions` và bucket `audio`, `series`.
   - Session và file của một user luôn nằm chung một project: lưu, compact, xoá chỉ đụng một project.
2. **Khoá ở shard là `user_id` (uid của Auth).** Không có mã thứ hai: uid là UUID ngẫu nhiên, không lộ
   email; ai có core thì có luôn bảng nối nên mã thứ hai không che thêm được gì. Giữ uid thì đường dẫn
   file (`{user_id}/...`), kiểm tra quyền và chữ ký các hàm repo không đổi, dữ liệu cũ không phải chuyển.
3. **`accounts(user_id, shard_ref, created_at)` ở core** (`0010_accounts.sql`). FK tới `auth.users`
   `on delete cascade`. RLS bật, không policy. `shard_ref` là `core` hoặc **project ref** của shard
   (phần đầu URL: `https://<ref>.supabase.co`). Ref không đổi và không phụ thuộc thứ tự trong `.env`,
   nên thêm, bớt, đổi chỗ các shard không làm user bị trỏ nhầm project. Migration ghi `core` cho mọi
   profile có sẵn.
4. **Gán shard lười.** `ShardRouter.shard_for(user_id, assign=...)`:
   - Ghi (tạo session, upload `audio`/`series`) mà chưa có dòng → chọn **project shard** ít user nhất
     (bằng nhau thì theo thứ tự trong `SUPABASE_SHARDS`); core không nằm trong danh sách chọn. Chỉ khi
     không cấu hình shard nào (dev, test) thì mọi thứ ở core. `insert ... on conflict do nothing` rồi
     đọc lại, nên hai request đầu tiên đến cùng lúc vẫn cùng một shard.
   - Đọc mà chưa có dòng → dùng core (user chưa có session nào), không tạo dòng.
   - Cache `user_id → shard_ref` trong RAM, vì giá trị không đổi.
   - Vẫn ghi `accounts` khi chưa cấu hình shard nào, để bật shard sau này không đưa nhầm user cũ đi.
5. **Định tuyến trong `Repos`, route không đổi.** `ShardedSessionRepo` và `ShardedAudioStore` cùng
   protocol với `SessionRepo`, `AudioStore`: bucket `audio`, `series` → shard của user; `avatars`,
   `baselines` → core. Shard ghi trong `accounts` mà không có trong cấu hình → `RuntimeError`.
6. **Cấu hình.** `SUPABASE_URL`, `SUPABASE_SERVICE_KEY` là core. `SUPABASE_SHARDS` là một JSON object
   `{"<project url>": "<service key>", ...}`, không đánh số. Mỗi shard có `ShardProject.number` = vị
   trí trong object + 1, **chỉ để hiển thị** (khớp tên `psc-shardNN`), không bao giờ lưu vào DB. Ref
   không trùng, không được là `core`. Có shard thì bắt buộc có core. Dev không có Supabase: memory
   repo, mọi thứ ở core.
   - Thêm shard: thêm một cặp vào object.
   - Bỏ shard: chỉ khi shard đó chưa có user; còn user thì request của họ báo lỗi
     (`Shard <ref> is not configured`), không trỏ nhầm sang project khác.
7. **Bảng `sessions` ở shard** (`shard/0001_sessions.sql`) cùng cột với core nhưng `user_id`,
   `script_id`, `baseline_id` không có FK (khác project). Code chỉ ghi hai id này, không đọc ngược sang
   `scripts` / `baselines`, nên id trỏ tới dòng đã xoá không gây lỗi. Job purge `insufficient_audio`
   chạy trên mọi shard (`shard/0002`, cùng nội dung `0005`).
8. **Xoá tài khoản** (bổ sung ADR-011): re-auth → xoá file 4 bucket (đi đúng project) →
   `delete_user_sessions` ở shard → xoá auth user (luôn cuối; cascade xoá `accounts`, `profiles`,
   `baselines`, `scripts`). Mỗi bước chạy lại được; bước 2, 3 lỗi thì trả 503 `storage_unavailable` và
   tài khoản còn nguyên, nên không có trường hợp mất tài khoản mà còn sót dữ liệu ở shard.

## Thiết lập

Migration cần chạy cho một project mới (core hoặc shard) và cách thêm shard: `architecture.md` mục
4.7. Mọi project đều cần extension `pg_cron`.

## Hệ quả

- 100 user ở mức trần: core giữ phần lõi của 100 user (~41 MB Postgres, ~44 MB Storage) cộng session
  của các user cũ ở `core`; 97 user mới chia cho 9 shard, 10–11 user mỗi shard: tối đa ~911 MB
  Storage (89%), ~323 MB Postgres (65%).
- Egress tính riêng mỗi project (5 GB/tháng): một shard 11 user có tối đa ~845 MB audio, mỗi file
  nghe lại được khoảng 6 lần mỗi tháng.
- Project Free tự tạm dừng sau 7 ngày không hoạt động; cả 10 project đều phải Restore trước demo.
- Chưa giới hạn số user mỗi shard hay tổng 100 user; chọn shard ít user nhất vẫn gán khi mọi shard đầy.
- Đọc session tốn thêm một truy vấn `accounts` ở lần đầu mỗi user sau khi server khởi động.
- Không chuyển user giữa các shard; thêm shard chỉ ảnh hưởng user mới.
