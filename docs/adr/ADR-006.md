# ADR-006: Optional layer 2 content moderation with Llama Guard via Ollama

- **Status:** Accepted
- **Date:** 2026-11-13
- **Scope:** `src/text_processing/moderation.py`

## Context

Layer 1 (a regex blocklist) is fast but only catches fixed phrases. The brief allows an optional layer 2: Llama-Guard-3-1B served by Ollama, assumed to run locally so that user text is not sent to an outside service (see "Update (2026-11-20): remote Ollama and wiring" at the end).

## Decision

1. Layer 2 runs only when `enable_llama_guard=True` and an `http://` or `https://` `ollama_url` is set (otherwise `ValueError`). When it is off, behaviour is the same as layer 1 alone (`layer="regex"`) and `fail_mode` has no effect.
2. A layer 1 block is final. Text that hits the blocklist or is too large is returned at once and Ollama is never called. Layer 2 does not undo layer 1 false positives; it only looks at text that already passed layer 1.
3. Normalized text is split into chunks of `layer2_max_chars=4000`, with at most `layer2_max_calls=8` calls (both provisional, not measured). One unsafe chunk makes the whole text unsafe and stops at once. More chunks than `layer2_max_calls` counts as unavailable.
4. An unavailable result (timeout, network error, status other than 200, JSON or output that cannot be understood) follows `fail_mode`:
   - `open` (default): allow, with `layer="regex"` and `reason="moderation_layer2_unavailable"`.
   - `closed`: reject, with `layer="llama_guard"`; `assert_safe` raises 503 `moderation_unavailable`.

   Unavailable decisions are never cached, so a short outage cannot lock or open the text for a long time. Every error at the I/O point (building the body, sending, parsing JSON, including deeply nested JSON) becomes unavailable, and only the exception type is logged. `KeyboardInterrupt` and programming errors outside the I/O point are not hidden. A lone surrogate in the text is replaced with U+FFFD before sending: otherwise httpx cannot encode it, and in `open` mode it could be used to skip layer 2. The rest of the text is still checked.
5. Llama Guard category codes (`S1` to `S14`) go into `flagged_terms`. `reason` is fixed and never shows model output. Logs contain only the layer, the allowed flag and the exception type, never the text, a term or the user id.

## Consequences

- Parser: ASCII only (`casefold` turns U+017F into `s`, so `ſafe` is rejected with `ValueError`). Only a single `safe` line is safe. A first line of `unsafe` is always unsafe (a valid `S<n>` code on line 2 goes into `flagged_terms`, otherwise it is `[]`). Any other form (for example `unsafe: S1`) is unavailable, so in `open` mode an unusual model output is allowed through. This is a known limit of the parser.
- The client created by default uses `trust_env=False` (user text does not go through a proxy from environment variables) and does not follow redirects. `ollama_url` must start with `http://` or `https://`. `trust_env=False` also ignores `SSL_CERT_FILE` and CA settings from the environment.
- `ollama_timeout_s` is ignored when the caller passes `http_client` (the caller sets timeout and proxy).
- Chunks do not overlap. Layer 2 receives text that is already case-folded and stripped of invisible characters, not the original.
- The Llama Guard 3 codes are `S1` to `S14`, but the regex accepts `S0` to `S99` (recorded only).
- The `httpx` logger at INFO level prints the URL of each request (internal). The text is not part of the URL.
- `fail_mode="open"` is a deliberate fail-open: layer 1 always runs, but when Ollama is down the text passes through layer 1 only.

## Known limits (for Security)

- **Coverage.** Normalized text longer than `layer2_max_chars * layer2_max_calls` (32,000 characters by default) is not checked by layer 2. `pipeline.py` joins the topic, the greeting (if any) and the first 20 document chunks into one string before calling `assert_safe`. A PDF has at most 10 pages, and if a page holds 3,000 to 4,000 characters (estimate, not measured) the total can reach 30,000 to 40,000 and pass 32,000.
  - `open`: a long document skips layer 2 completely (only a warning is logged; the pipeline does not use the reason today). An attacker can pad the text past 32,000 characters on purpose to avoid layer 2.
  - `closed`: a document over the limit gets 503 "temporarily unavailable", but retrying always fails (the condition is deterministic), so "temporarily" is misleading. A separate error code such as `too_many_chunks` is worth considering (later work; it needs approval because it touches the `contracts.py` contract).
- **Hidden characters.** Layer 2 gets the text with hidden characters removed, not replaced by a space, so `how<ZWSP>to` becomes `howto` (words glued together). An attacker who replaces spaces with ZWSP can make layer 2 less likely to recognize the text. Layer 1 is not affected because it scans both variants. Sending a version with spaces has a cost: a hidden character INSIDE a word (for example a soft hyphen from a PDF) would split the word. Not decided; waiting for Security. The code is unchanged.
- **Prompt injection.** Llama Guard is a content risk classifier, not a dedicated prompt-injection detector.
- **No deadline and no circuit breaker.** The 10 s timeout applies to each phase (connect, read, write, pool) and is not measured, so one call can take much longer. Up to 8 chunks are called one after another with no total deadline. Unavailable results are not cached, so when Ollama hangs every request pays one more timeout.
- **Fail-open default.** When Ollama is down, content passes layer 1 only.

## Unverified assumptions

- When this ADR was written, no real Ollama call had been made. The model tag `llama-guard3:1b`, `/api/chat` applying the Llama Guard template by itself (we send no system prompt), and the reply format `safe` / `unsafe\nS1,S2` were assumptions. Tests use `httpx.MockTransport`. Since then the team lead has called the remote Ollama API and it replied (see the Update below), but the request, the model tag, the reply format and the latency were not recorded here, so they are still undocumented. Record them, with the date and who ran the call, before layer 2 is relied on in production.
- Ollama context: `options` only sets `temperature`, not `num_ctx`. A 4,000-character chunk plus the Llama Guard prompt may exceed Ollama's default context (unverified), especially for Vietnamese with diacritics or CJK, which use many tokens. Escaping `<` as `&lt;` can make the text up to 4 times longer. If so, Ollama truncates or fails, the output cannot be parsed or returns 500, and in `open` mode the text passes with the unavailable reason. `num_ctx` and token length must be measured before choosing `layer2_max_chars`.
- RAM and cold start of the model are not measured. The first call may exceed the timeout; in `open` mode it passes with the unavailable reason.

## Open questions for Security

1. Default `fail_mode`: `open` (current) or `closed`.
2. Hidden characters in the text sent to layer 2: replace with a space or remove.
3. A separate error code for text over the chunk limit in `closed` mode.
4. Whether layer 2 may ever overrule a layer 1 block (current decision: no).
5. The starting blocklist, which blocks quoted text such as a lecture about prompt injection.
6. Whether user text may be sent to a remote Ollama server, and whether `fail_mode` should stay `open` now that layer 2 is on for everyone who sets `OLLAMA_HOST`.

## Alternatives considered

- **Layer 2 may overrule a layer 1 block.** It would remove false positives such as quoted text. Rejected: a model should not reverse a deterministic block (it opens a path for injection), the brief says layer 1 is always on, and it costs extra calls.
- **Send only the first part of the text.** The simplest option. Rejected: harmful content placed after the cut would pass completely.
- **Send the whole text and raise `num_ctx`.** Rejected for now: RAM and latency are not measured, and the real context limit is unknown.
- **Default to `closed`.** Rejected as the default: when Ollama is off (for example for RAM reasons, R-6) every request would get 503 and the whole system would stop. Still to be confirmed by Security.

## Update (2026-11-20): remote Ollama and wiring

Since this ADR was written, `moderation.py` and `main.py` have changed:

- If `ollama_url` ends with `/chat/completions`, the client sends an OpenAI-compatible request and reads `choices[0].message.content`; otherwise it keeps `/api/chat`. A non-empty `ollama_api_key` is sent as `Authorization: Bearer`.
- `main.py` builds the moderator with `enable_llama_guard=bool(settings.ollama_host)`, so layer 2 is ON whenever `OLLAMA_HOST` is set. `fail_mode` is not passed, so it stays `open`.
- The team's `.env` points `OLLAMA_HOST` to a remote server. User text (topic, greeting, up to 20 chunks, and the text of a script being saved) therefore leaves the application server. This differs from the local-server assumption in Context and needs Security's acceptance. The key must never be logged.
- `pipeline.py` still ignores the decision returned by `assert_safe`, so the `moderation_layer2_unavailable` flag does not reach the user.
