# ADR-015: Anti-spam limits for script generation and Regenerate

- Status: Proposed
- Date: 2026-11-26
- Refs #121. Use case UC3 (Generate Script). Related: ADR-013 section 4.
- Code: `src/app/script_limits.py`, `generate_script_endpoint` in `src/app/main.py`,
  `RateLimitRepo.retry_after_s`, `ScriptGenerationPipeline.has_active_job`,
  `app_constants.toml` `[script_limits]`.

## Context

`POST /api/generate-script` had no limit, and every run may call the LLM provider. A user can
press Regenerate or start a new chat again and again. ADR-013 already added fixed-window
counters in Postgres (`hit_rate_limit`, migration 0011).

## Decision

Order inside the endpoint. A step that refuses the request stops it.

| Step | Check | Answer |
|---|---|---|
| 1 | Read the chat session (it can supply topic, category and duration) | - |
| 2 | Topic not empty, duration allowed, feedback within `[web] composer_max_words` | 422 `output_invalid`, nothing counted |
| 3 | No running job of this user | 429 `job_running`, nothing counted |
| 4 | Count the rate limit layers | 429 with the reason of the first full layer |
| 5 | Save the uploaded PDF | upload errors as before |
| 6 | Check the running job again, then create the job with no `await` in between | 429 `job_running`, saved PDF removed |

Since [ADR-017](ADR-017.md) (proposed), the gibberish guard (422 `gibberish_input`) and then the local category guard (422 `category_mismatch`) run between steps 2 and 3, so a request they refuse is not counted.

A request with non-blank `user_feedback` is a Regenerate. Layers, in counting order:

| Reason | Bucket | Applies to |
|---|---|---|
| `cooldown` | `script_regen_cooldown` (one hit per cooldown; longer for long speeches) | Regenerate |
| `generate_quota` | `script_gen_window` (Generate and Regenerate together) | both |
| `regenerate_quota` | `script_regen_window` | Regenerate |

- The key is the SHA-256 of the user id. All limits live in `[script_limits]`. They are
  provisional and not yet measured.
- 429 answer: header `Retry-After: <seconds>` and body
  `{error_code: "rate_limited", message, retry_after_s, reason}`.
- Fail open: when `hit()` fails, that layer is skipped with a warning and later layers still
  run. When only `retry_after_s()` fails, the request stays refused and the wait is the whole
  window. Warnings name the bucket only.
- Planned UI behaviour (separate web PR, not implemented here): `cooldown` and
  `regenerate_quota` lock Regenerate; `generate_quota` and `job_running` lock both Generate and
  Regenerate.

## Consequences and known limits

- Refused requests can still use attempts, because `hit()` counts and checks in one step.
  Hand count with a 15 s cooldown, 5 Regenerate and 10 total per 600 s (checked in
  `tests/test_regenerate_rate_limit.py`): Generate at t=0 and Regenerate at t=20, 35, 50, 65,
  80 pass. At t=95 the Regenerate quota refuses (wait 525 s) after one total attempt was used.
  Retries at t=110, 125, 140 use three more. At t=155 the total is full (wait 445 s) after only
  6 accepted requests, so a plain Generate is refused too.
- A Regenerate refused by a later layer has already started a new cooldown.
- A blank `user_feedback` counts as Generate, so a client that drops the feedback on purpose is
  stopped only by the total limit: 10 answers 202, then 429 (checked in the same test file).
- `retry_after_s` describes the refusing layer only; another layer may still be full after it.
- Fixed windows allow up to twice the maximum around a window edge.
- One cooldown bucket: its length comes from the request being checked, not from the previous
  one. The duration is what the client sends or the session holds, so a request that names a
  long template with a short duration gets the short cooldown.
- The cooldown starts when the previous Regenerate was submitted. If generation takes longer
  than the cooldown, the user does not notice it. Generation time is not measured.
- The running-job check covers one process only. A job still active `active_job_stale_s` after
  it was created is ignored, so a run slower than that no longer blocks a second one.
- New chat or Try again while the old job is still running answers `job_running`.
- Provider errors, moderation rejections, cache hits and upload errors happen after counting, so
  those requests still use attempts.
- Two Generate requests that race each other can use two attempts although one job is created.
- The new buckets live in `auth_rate_limits`, although the table name says auth and the comment
  in migration 0011 lists only the account buckets. The SQL is not changed.
- It is not confirmed that 0011 has run on `psc-main`. Where it has not, these limits fail open;
  only the running-job check still works.
- `retry_after_s` on Supabase compares the server clock with Postgres time and adds 1 s. The
  margin is a heuristic, not measured.

## Alternatives considered

| Alternative | Why not chosen |
|---|---|
| Counters in RAM | Lost on restart and counted per worker (the problem ADR-013 solved) |
| Redis | One more service for a few counters; Postgres is already there |
| Read the counter before `hit()` | One more query per layer and `hit()` still decides; parallel requests can pass the read and still use attempts while being refused |
| Two cooldown buckets (short and long) | Switching the duration would skip the other cooldown |
| `has_generated_script` in the chat session | The web UI always sends non-blank feedback for Regenerate and its Try again; the total limit stops a client that drops it; `chat_session.py` stays unchanged |
